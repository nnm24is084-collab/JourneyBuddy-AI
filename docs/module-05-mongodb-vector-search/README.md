# Module 2.5: MongoDB Atlas and Vector Search



## 1. Objective



Design a unified document schema that stores content and its metadata alongside a high-dimensional vector field. Document the approximate nearest-neighbor (ANN) vector index specification used to retrieve semantically relevant documents.



This module focuses on schema design and vector-search architecture.



## 2. Overview



MongoDB Atlas is a managed database platform that supports document storage and vector search. Vector search can retrieve documents based on the similarity between their vector embeddings and a query embedding.



For JourneyBuddy-AI, this architecture could support semantic retrieval of internship descriptions, skills, and career-related information.



This is a proposed design; it does not imply that MongoDB Atlas Vector Search is already configured in the project.



## 3. Proposed Document Schema



Each document contains content, metadata, and an embedding vector.



Example document:



```json

{

&#x20; "\_id": "internship-001",

&#x20; "content": "Data Science internship involving Python and machine learning.",

&#x20; "metadata": {

&#x20;   "author": "Career Team",

&#x20;   "category": "Data Science",

&#x20;   "timestamp": "2026-10-14T10:00:00Z"

&#x20; },

&#x20; "embedding": \[0.12, -0.08, 0.31, 0.45]

}

```



The embedding values above are illustrative only. A real embedding must be generated by an embedding model, and its vector dimension must match the configured index.



### Field descriptions



| Field | Purpose |

|---|---|

| `\_id` | Unique document identifier |

| `content` | Text or information to retrieve |

| `metadata.author` | Author or source of the document |

| `metadata.category` | Classification used for filtering |

| `metadata.timestamp` | Time associated with the document |

| `embedding` | Numeric vector representation of the content |



The timestamp should use a consistent format. In a real MongoDB collection, it can be stored as a BSON Date rather than a string.

## 5. Approximate Nearest-Neighbor Search



ANN search retrieves vectors that are close to a query vector without necessarily comparing every stored vector exhaustively.



The workflow is:



1\. Store documents and their metadata.

2\. Generate embeddings for the document content.

3\. Build a vector index on the embedding field.

4\. Generate an embedding for the user's query.

5\. Search the vector index for the nearest matching vectors.

6\. Apply supported metadata filters when required.

7\. Return relevant documents and their similarity scores.



## 6. Proposed Vector Index Specification



A conceptual index definition is shown below. The actual vector dimensions must be chosen to match the embedding model.



```json

{

&#x20; "fields": \[

&#x20;   {

&#x20;     "type": "vector",

&#x20;     "path": "embedding",

&#x20;     "numDimensions": 1536,

&#x20;     "similarity": "cosine"

&#x20;   },

&#x20;   {

&#x20;     "type": "filter",

&#x20;     "path": "metadata.category"

&#x20;   },

&#x20;   {

&#x20;     "type": "filter",

&#x20;     "path": "metadata.author"

&#x20;   }

&#x20; ]

}

```



### Index field descriptions



\- `path`: Identifies the document field containing vectors or filterable metadata.

\- `numDimensions`: Defines the expected vector dimension.

\- `similarity`: Selects the similarity metric used to compare vectors.

\- Filter fields: Allow supported metadata filters to narrow the search.



The dimension `1536` is an example, not a requirement. It must be changed if the selected embedding model produces a different vector size.



The index definition must be adapted to the current MongoDB Atlas Vector Search index syntax and deployed configuration.



## 7. Cosine Similarity



Cosine similarity measures the cosine of the angle between two vectors. It is commonly used to compare embedding vectors.



\\\[

\\operatorname{cosine}(A,B)=

\\frac{A\\cdot B}{\\|A\\|\\|B\\|}

\\]



A higher cosine similarity generally indicates a closer directional match between vectors. The precise score interpretation depends on the embedding model and the chosen metric.
